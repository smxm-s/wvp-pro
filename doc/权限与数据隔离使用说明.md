# 权限与数据隔离使用说明

> 本文档描述 wvp-GB28181-pro 在本项目中扩展的**两级权限体系**：
> **功能权限**（能不能用某个功能）+ **数据权限**（能看哪些摄像头）。
>
> 这两部分是在上游开源版本基础上新增的能力，不是原生功能。

---

## 一、总体设计

```
                    登录
                     │
        ┌────────────┴────────────┐
        │  角色（wvp_user_role）   │  ← 决定"能不能用某个功能"
        │  authority = 权限码列表   │
        └────────────┬────────────┘
                     │
        ┌────────────┴────────────┐
        │ 数据范围（wvp_user_region）│  ← 决定"能看哪些区域"
        │  用户绑定的行政区划节点     │
        └─────────────────────────┘
```

| 层级 | 解决的问题 | 存储 | 强制位置 |
|------|-----------|------|---------|
| **功能权限** | 该角色能不能执行这个操作 | `wvp_user_role.authority`（逗号分隔权限码） | 后端 `@PreAuthorize` + 前端菜单/按钮 |
| **数据权限** | 该用户能看到哪些区域的通道 | `wvp_user_region`（用户 ↔ 区划节点） | 后端查询过滤 + 点播鉴权 |

### 2.3 超级管理员

`wvp_user_role.id = 1`（admin）是**超级管理员**，代码中直接放行，拥有全部权限：

- 不需要在 `authority` 里配任何权限码；
- `/api/user/permission` 会返回 `superAdmin: true`；
- 前端菜单全部显示、所有按钮显示、路由不做拦截。

**该角色不可被修改或删除**（`RoleMapper` 的 SQL 里带 `id != 1` 条件，Controller 里也做了拦截）。

## 三、后端实现

### 3.1 核心组件

| 文件 | 作用 |
|------|------|
| `conf/security/Permission.java` | 权限点枚举（唯一出处） |
| `conf/security/PermissionService.java` | Bean 名 **`perm`**，提供 `has(code)` / `hasAny(...)` / `getCurrentPermissions()` |
| `conf/security/JwtAuthenticationFilter.java` | 把数据库中的**完整角色（含 authority）**放进登录上下文 |
| `conf/GlobalExceptionHandler.java` | 鉴权失败统一返回 `403 {"code":403,"msg":"无权限访问"}` |

### 3.2 如何使用

在任意 Controller 方法上加注解即可：

```java
@GetMapping("/list")
@PreAuthorize("@perm.has('device:view')")
public PageInfo<Xxx> list(...) { ... }
```

多权限任一命中：

```java
@PreAuthorize("@perm.hasAny('device:edit','org:edit')")
```

> 项目已开启 `@EnableGlobalMethodSecurity(prePostEnabled = true)`，无需额外配置。

### 3.3 放行规则（重要）

`PermissionService.has()` 在以下情况**直接放行**：

1. `user-settings.interface-authentication = false` —— 关闭接口鉴权时不做权限校验，避免误伤；
2. 当前用户角色 `id = 1`（超级管理员）；
3. 权限码为空。

### 3.4 自助接口（不鉴权）

以下接口**故意不加权限**，保证任何登录用户都能用：

- `POST /api/user/changePassword` —— 修改自己的密码（默认密码强制修改流程依赖它）
- `POST /api/user/userInfo` —— 查询自己的信息
- `POST /api/user/logout`

### 3.5 对外接口

| 接口 | 权限 | 说明 |
|------|------|------|
| `GET /api/user/permission` | 登录即可 | 当前用户的 `{roleId, roleName, superAdmin, permissions[]}` |
| `GET /api/role/all` | `user:view` | 角色列表（`authority` 为逗号分隔字符串） |
| `POST /api/role/add` | `user:edit` | 新增角色（仅超管） |
| `POST /api/role/update` | `user:edit` | 修改角色（仅超管，不可改 id=1） |
| `DELETE /api/role/delete` | `user:edit` | 删除角色（仅超管，不可删 id=1） |
| `GET /api/role/permission/all` | `user:view` | 全部权限点（按分组），供权限树渲染 |
| `GET /api/user/region?userId=` | `user:view` | 查询某用户绑定的区域ID列表 |
| `POST /api/user/region/save` | `user:edit` | 保存绑定，参数 `userId`、`regionIds`（逗号分隔，空字符串表示清空；仅超管） |

### 4.1 按钮级控制

```html
<el-button v-permission="'device:edit'">编辑</el-button>
<el-button v-permission="['device:edit','org:edit']">批量</el-button>
```

### 4.2 三层拦截

1. **菜单**不显示（侧边栏过滤）
2. **路由**进不去（直接输地址会被重定向到 404）
3. **接口**调不通（后端 `@PreAuthorize` 返回 403）

### 4.3 权限刷新时机

- 登录成功后拉取一次；
- **每次应用加载（刷新页面）时重新拉取一次** —— 因此管理员调整了角色权限后，用户**刷新页面即可生效**，无需重新登录。

## 五、数据级隔离（区域）

### 5.1 数据模型

```sql
-- 用户 ↔ 行政区划节点
create table wvp_user_region (
  id          serial primary key,
  user_id     int          not null,
  region_id   int          not null,   -- 对应 wvp_common_region.id
  create_time varchar(50)  not null,
  constraint uk_user_region unique (user_id, region_id)
);
```

**匹配规则**（与项目原有"通道管理"实现保持一致）：

```
通道的 coalesce(gb_civil_code, civil_code)  ==  区划节点的 device_id      （精确相等）
```

> ⚠️ 注意是**精确相等**，不是前缀匹配。且 `gb_civil_code` 优先于 `civil_code`。

### 5.2 生效规则

| 用户情况 | 可见范围 |
|---------|---------|
| 超级管理员（role_id=1） | 全部 |
| 非超管、**未绑定**任何区域 | 全部（向后兼容；未启用隔离） |
| 非超管、**已绑定**区域 | 仅"绑定区域 **及其所有下级区域**"内的通道与所属设备 |

> 安全提示：当前采用**未绑定即不受限**（fail-open）的策略，好处是不会影响已有账号。
> 如果要求严格隔离，请把**所有非超管用户**都绑定至少一个区域。

### 5.3 已覆盖的过滤入口

| 入口 | 实现方式 |
|------|---------|
| 通道列表（`/api/common/channel/list`、`/civilcode/list`、`/parent/list`） | 在 `ChannelProvider` 的 WHERE 拼接 `coalesce(gb_civil_code, civil_code) in (...)` |
| 设备列表（`/api/device/query/devices`） | `DeviceMapper.getDeviceList` 增加 `EXISTS` 子查询（分页 total 与实际返回天然一致） |
| 点播鉴权（`/api/common/channel/play`、`/api/play/start/{deviceId}/{channelId}`） | 方法体内校验通道是否在允许范围内，否则抛 403 |

### 5.4 尚未覆盖的入口（如需隔离请另行改造）

- 电子地图点位（`/api/common/channel/map/list`）
- 报警列表
- 云端录像列表
- 录像回放查询（`/api/common/channel/playback/query`）
- 国标级联向上推送的通道

### 5.5 操作方式

1. 管理员登录 → **用户管理**
2. 找到目标用户 → 点「**负责区域**」
3. 在行政区划树里勾选该用户负责的区域（支持多选，勾父节点即代表其整个下级）
4. 保存 → 该用户**刷新页面**生效
5. **不勾任何区域 = 不受限制**

## 六、日常运维指南

### 6.1 新增一个角色

1. 管理员登录 → **用户管理** → 「**角色管理**」→ 新增
2. 填角色名 + 勾选权限 → 保存
3. 到「用户管理」→ 添加用户 → 用户类型里就能选到新角色

### 6.2 调整某个角色的权限

同上进入「角色管理」→ 编辑 → 重新勾选权限 → 保存。
该角色下的用户**刷新页面**后生效。

### 6.3 给用户限定区域

见 5.5。

### 6.4 新增一个权限点（需改代码）

1. 在 `Permission.java` 里加一个枚举项（`code` / `name` / `group`）；
2. 在需要管控的 Controller 方法上加 `@PreAuthorize("@perm.has('新权限码')")`；
3. 到「角色管理」里给相应角色勾上；
4. 如需前端控制按钮，用 `v-permission="'新权限码'"`。

## 七、已知限制与注意事项

1. **数据隔离仅覆盖 5.3 列出的三个入口**，其余入口（地图、报警、云录像、回放、级联）未做隔离。
2. **未绑定区域 = 不受限**（fail-open），严格场景请给所有非超管用户绑定区域。
3. 区域绑定弹窗采用 `check-strictly`（父子不联动）+ 默认展开全部；
   提交时**只提交全选节点**，下级区域由后端自动展开 —— 因此勾父节点即可覆盖整个下级。
4. 行政区划节点的 `device_id` 请使用**真实的国标行政区划编码**（本项目现有树组件的展开逻辑是
   `deviceId 长度 ≤ 8 才继续下钻`，若使用过长的自定义编码，树将无法展开下级）。
5. `RoleMapper` 与 `RoleController` 均对 `id = 1` 做了保护，超管角色改不了也删不掉。
6. `wvp_user_role.authority` 已从 `varchar(50)` 扩到 `varchar(1000)`，
   增加权限点时注意不要超出长度。
